# Доклад: local_code_worker на задаче discountprice_checker (защита сайта, заглушка)

*21–22.10.2026. Задача для агента (дословно, пунктами):*
1. *Изучить возможные способы защиты сайта для этого проекта и улучшить её, избегая конфликтов и закрытия сайта.*
2. *Посмотреть проблему с периодическим отключением сайта (переходом на заглушку): найти причину и устранить.*

*Работу (и поиск причины, и правки) выполнял local_code_worker (gpt-oss-20b) в изолированном worktree.
Я наблюдал за прогонами, искал, почему агент не справляется, и исправлял harness.

## Что на самом деле происходит с сайтом (контрольная картина)

Нужна, чтобы оценивать выводы агента. Собрана по логам nginx в ВМ (только чтение) до того, как стало ясно,
что расследование тоже должен делать агент. Агенту эти сведения не передавались.

- В ВМ (с 18.10) заглушка включалась 18.10 около 08:20, 19.10 (много раз с 04 до 15 ч) и 20.10 около 21:09.
- Причина — guard закрывал сайт из-за **одного** адреса: 18.10 08:20 сканер `79.124.58.82` сделал 1380 запросов
  за минуту, nginx ответил на 576 из них 429. Старый порог `guard_429_limit = 300` сработал как «DDoS».
  20.10 21:09 — то же с `147.224.220.170` (282 ответа 429).
- 21.10 пороги подняли (1500/6000) и включили автооткрытие через 30 минут. С тех пор закрытий не было. Но правило
  осталось прежним: один бот, который получает больше 1500 ответов 429 в минуту, по-прежнему закроет сайт.
- Telegram из ВМ недоступен: 1624 неудачные отправки в журнале guard. Владелец не узнаёт о закрытии.
  Кроме того, в ВМ нет базы, и guard на каждое событие пишет предупреждение `No module named 'app.db'`.

## Итог по discountprice_checker

В рабочую копию ничего не перенесено: ни одна правка агента не годится в работу целиком.
- Лучший результат — прогон 13. Причину агент нашёл сам и верно: сайт закрывался из-за трафика **одного** адреса
  79.124.58.82 (1380 запросов за час, 576 ответов 429). Но правка исключает из подсчёта запросы с UA «Googlebot»,
  а этот «Googlebot» и есть тот же атакующий адрес. Такая правка ослабила бы защиту.
- В прогонах 5–7, 12, 15 и 17 правки — «белые списки» и подъём порогов. Правило «один адрес закрывает весь сайт»
  они не меняют.
- Чего не хватает (сначала причина, потом правки): засчитывать DDoS и закрывать сайт, только если запросы идут
  со многих адресов (одиночный адрес и так режет nginx — 429/444), а одиночный адрес — сообщать как flood.
  Не считать подозрительными `/.well-known/acme-challenge/`. Не писать в журнал ВМ предупреждение
  `No module named 'app.db'` на каждое событие. Доставлять сообщения guard владельцу (Telegram из ВМ недоступен).

## Изменения local_code_worker

**Новые инструменты агента**
1. `logstats` — сводка лога вместо чтения целиком: число строк, интервал времени, поля JSON, топ значений
   (`by=status|ip|uri|…`, `by=message` для текстовых логов — числа и время нормализуются, одинаковые сообщения
   склеиваются), пики по минутам/часам/дням (`bucket`), последние N строк (`show`), фильтр `match`.
   Понимает JSON-логи nginx, текстовые логи и `.gz`. Предупреждает, если последняя запись старше 2 дней.
2. `test` — pytest проекта через его venv с коротким отчётом: имя теста, место (файл:строка), строки `E`,
   итог. Если `path` — исходный модуль, запускаются тесты, которые его импортируют.
3. `refs` — все упоминания имени целым словом, с типом (`def`/`import`/`use`) и охватывающей функцией.
   Для snake_case-настроек находит и `ИМЯ_В_ВЕРХНЕМ_РЕГИСТРЕ` (.env, документация). Отдельно сообщает,
   упоминается ли имя в тестах.

**Расследования (пункты «найти причину / посмотреть проблему / изучить»)**
- К пункту добавляется подсказка: где лежат логи проекта, в каких документах описан сервер. Из документации
  извлекаются готовые команды только для чтения (без `rm/nano/restart`, без `tail -f`); `%USERPROFILE%` для Git Bash
  заменяется на `~`. Там же объяснено, как сохранить лог сервера в `logs/` и разобрать его через `logstats`.
- `decide` по такому пункту не принимается, пока агент не посмотрел логи. Если смотрел только устаревшие, а сервис
  по документации работает на сервере, нужен свежий лог. Ещё нужна причина `cause`, в которой есть хотя бы один
  факт (время, адрес, число), реально встречавшийся в выводе инструментов.

**Стабильность**
- pytest на этой машине падал ещё до запуска тестов (WinError 5 на `pytest-current`). Из-за этого harness считал
  бы тесты проваленными. Теперь каждый прогон pytest (harness, `run`, `test`, проверка «было/стало») идёт со своим
  `--basetemp`.
- Worktree: `logstats`, `grep`, `glob` и `read` находят логи и данные из .gitignore в основной копии проекта.
- `edit`: `+` в начале добавленных строк (разметка диффа) снимается; после неудачной правки сбрасывается пометка
  «файл уже прочитан», поэтому повторное `read` показывает текст, а не заглушку.
- `run logstats|refs|symbols|test …` выполняется как вызов инструмента: модель путает инструменты с программами.
- Новая проверка в конце хода: изменён модуль, у которого есть тесты, но ни один тест не добавлен →
  агент возвращается писать тест на новое правило. Проверка идёт после прогона тестов проекта.
- Пустой шаблон `glob` показывает всё содержимое папки.

**Сбор и проверка фактов harness'ом (прогоны 8–16)**
- Готовые команды скачать лог сервера (только чтение, с ротированными файлами). Если модель дважды не идёт
  за логами, harness скачивает их сам и выдаёт сводку.
- Проверка причины: за названный час — топ адресов и статусов; адреса из причины пересчитываются по логам;
  без времени и адреса — пики свежего лога. Вывод формулируется явно («98% запросов часа — с одного адреса»).
- Предупреждение об исключениях по данным клиента (User-Agent, заголовки) с проверкой «бот X шёл с N адресов».
- Коды HTTP-статусов фактом не считаются. Неподтверждённая причина помечается в решениях для пользователя.
- Проверки конца хода: «изменения без тестов», «удалены существующие тесты».
- Сбой формата вызова: больше повторов, и подсказка каждый раз другая.

## Что осталось

- Модель плохо отличает гипотезу от факта и тянется к простым правкам («белый список», «поднять порог»).
  Гейты заставляют её смотреть логи, но не гарантируют вывод, который следует из них.
- Сбои формата вызова инструментов (harmony) остаются частыми: 3–6 повторов за прогон.
- Прогон занимает 20–40 минут, результат сильно зависит от прогона. Оценивать по нескольким.
